# Pishoo 受限远程终端：WASM Shell 与原生命令

日期：2026-09-23。状态：设计提案，未实现。本文讨论的 `home` 是**启动 Pishoo 的系统账号的 home**，不是 DHTTP Server 的目录，也不是为 Alice 创建的 Unix 账号。文中“SSH”沿用产品称呼；现有 DShell over WebTransport 与规划中的 HTTP/3 Extended CONNECT 均不是标准 SSH 协议，标准 `ssh` 客户端兼容性不由本设计自动获得。

## 目标与权限边界

经明确授权的 DHTTP 身份可以打开交互终端，读写 Pishoo 运行账号 home 中的普通文件，使用常见 CLI，包括需要启动原生子进程的命令。Pishoo 的身份私钥和控制面文件不可通过终端读取或修改。远程终端不获得 Pishoo 进程的内存、文件描述符、DHTTP 签名能力或管理 API 凭据。

这个权限范围接近实例管理员。Pishoo 的一个运行账号可以承载多个 DHTTP Server，因此“访问某个 Server 的自身身份”**不自动授予**该账号的 home 终端。只有实例配置中显式列出的终端管理员身份可以连接。终端身份与目标 Server 的关系、撤销和审计由 Pishoo 在实例化 WASM 前强制执行，不由 `shell.wasm` 自报。

本设计对“home 除敏感目录外均可访问”的精确定义是：终端看到一个受控的 `/home` 文件视图，可以读写其中非保留内容；它不意味着把真实 `$HOME` 直接预打开给 WASM。Pishoo 的整个 `state-dir`（包括 `ssl/`、`db/config.db`、`db/access.db`、Lib 部署文件和运行时控制文件）是首个保留范围。其他账号密钥和凭据目录，例如 `~/.ssh`、云服务凭据，必须由实例管理员明确决定是否放入保留范围；若开放，就按普通 home 内容视为终端可读取和传出。

## 结构

```text
远端终端客户端
  │ DHTTP 已认证的双向会话
  ▼
Pishoo 主进程：认证、准入、配额、会话生命周期；持有 Endpoint/私钥
  │ 仅传会话流和已批准的策略，不传私钥或 state-dir 句柄
  ▼
受操作系统隔离的 pishoo-terminal 子进程
  ├─ Wasmtime：运行 shell.wasm，负责提示符、解析、内建命令和作业控制
  ├─ WASI 文件视图：/home 可读写、/tmp 会话私有、工具目录只读
  └─ exec 宿主接口：在**同一个受限文件/进程/网络视图内**启动原生 CLI
```

WASM 是终端程序，不是网络认证层。Pishoo 处理传输、可信身份和入站授权；终端子进程接收已认证的会话流。若继续使用 Extended CONNECT，需要定义 stdin/stdout/stderr、窗口大小、信号、退出码和取消的线格式；若继续使用现有 DShell，需做协议适配。两者都不应把 TLS/Endpoint 私钥交给 WASM。

每个会话启动独立的终端子进程和 WASM Store；同一会话中的原生命令是该子进程的后代，并在同一操作系统沙盒中执行。`shell.wasm` 不从任意请求加载，固定由受信任的 Pishoo 发行版或实例管理员安装；用户可写的 home 不能覆盖它。会话之间不共享可变 WASM 内存或临时目录。

## 能力表

| 能力 | 终端内的范围 |
| --- | --- |
| 文件 | 受控 `/home` 读写；私有 `/tmp` 读写；已批准的 CLI 程序、动态库和系统数据只读。保留目录完全不可见。 |
| 原生进程 | 允许在同一 OS 沙盒内运行普通 CLI，支持参数数组、工作目录、管道、PTY、信号和退出码。不得在 Pishoo 主进程的权限视图中启动。 |
| Pishoo 管理 | 默认无直接读取/修改 `state-dir` 的能力。需要的 CLI 管理动作另做经过身份授权的窄接口；不能借用宿主内部数据库连接。 |
| 网络 | 单独配置出站范围；若开放通用网络，终端可传出其可读的全部 home 内容。不能访问 Pishoo 的私有 IPC、继承 Endpoint 身份或调用签名能力。 |
| 环境与设备 | 传入最小环境、固定 PATH、`HOME=/home`；不继承 Pishoo 的环境变量和 FD；只开放终端需要的 PTY，不开放原始设备、宿主 `/proc` 或调试接口。 |
| 提权 | 禁止 setuid/特权能力、`sudo`、容器和挂载逃逸；子进程不能追踪、注入、终止 Pishoo 主进程。 |
| 资源 | 每会话和实例限制 CPU、内存、进程数、FD、输出缓冲、磁盘写入和最长空闲时间；断连后终止进程组并回收。 |

`exec` 接口接受程序与 `argv[]`，并返回受控的进程句柄及流；shell 语法由 WASM 解析。即便允许用户输入 `sh -c ...`，`sh` 也必须在同一 OS 沙盒中运行。只在 WASM 中校验命令字符串、路径前缀或程序名，不能约束原生程序自己发起的文件打开、子进程和网络访问。

## 文件视图与敏感目录

Wasmtime 的普通 `preopened_dir($HOME, "/home", ReadWrite)` 会授予整个子树，不能靠“不单独挂载 ssl”排除 `$HOME` 里的子目录（见 [Wasmtime 的 preopen 说明](https://docs.wasmtime.dev/api/wasmtime_wasi/struct.WasiCtxBuilder.html#method.preopened_dir)）。因此不能直接使用真实 `$HOME` 作终端的 WASI preopen。应先为终端子进程建立受控的文件系统视图，再把其中的 `/home` 预打开给 WASM；原生命令也必须只看到这个视图。视图构建失败时拒绝会话，不能退回到真实 home。

保留范围不是仅按路径字符串过滤。实现要处理相对路径、符号链接、硬链接别名、大小写和 Unicode 规范化、目录重命名、并发路径替换、其他挂载点、`/proc/*/fd` 与继承的 FD，以及 Unix socket 等非文件入口。若这些入口无法在某平台验证为受限，禁用该平台的原生命令模式。Pishoo 主进程读取 `ssl/` 与终端不可见并不矛盾；两者运行在不同的文件和进程权限视图中。

保护范围还要覆盖可让终端**间接**获取私钥或改变授权的内容：Pishoo 状态库、Lib/路由部署文件、可被守护进程执行的脚本或二进制、更新渠道以及管理 socket。只隐藏 `ssl/` 却允许改写这些控制面文件，不能保证私钥或服务授权仍受保护。

## OS 沙盒要求与跨平台界限

支持原生 CLI 意味着 WASM 的能力限制不再是唯一边界。终端子进程及全部后代需要独立的 OS 级文件视图、进程隔离和资源限制。Linux 版本可以评估用户/挂载/PID 命名空间、只读工具挂载、受限 home 视图、无特权能力和系统调用限制的组合；具体能否在 Pishoo 的非 root 安装下建立，必须先做运行验证。仅 `chroot`、仅更改工作目录、仅隐藏 WASI preopen，均不算完成隔离。

macOS 需要能覆盖子进程及其后代的等效强制隔离，并验证它确实保护目录、进程和 IPC。未实现并通过验证的平台只提供纯 WASM 命令模式，或拒绝开启远程终端；不能静默改用 Pishoo 的运行账号直接执行原生命令。

如果产品要求所有平台立刻可用，可先把常用文件工具和 Pishoo 的安全管理操作实现为 WASM/WASI 命令；这能复用 WASI 的文件能力，但不等于兼容宿主机上任意已安装的原生 CLI。需要“多数原生 CLI”时，再交付 OS 沙盒及 `exec`。

## 实施顺序与验收

1. 固定终端管理员 DHTTP 身份与会话授权；协议、审计和取消由 Pishoo 主进程处理。
2. 建立终端子进程与受控 home 视图，只运行最小 `shell.wasm`；确认敏感路径和 Pishoo 内存/FD/IPC 均不可达。
3. 在同一 OS 沙盒内增加 `exec`、PTY/管道和进程组回收；先支持固定测试命令，再开放普通 CLI。
4. 验证常用文件命令、编辑器、构建工具和网络工具的可用性，并按实际需求调整只读工具目录与出站策略。

必须包含的反例：`cat` 直接读私钥；经链接、`..`、备用挂载和 FD 读私钥；修改 `db/config.db`/`access.db` 或替换 Lib/主程序后间接取得权限；从子进程读 Pishoo 环境/内存或连接私有 IPC；在 WASM 中和 `exec` 后分别执行相同文件操作，结果一致；断线后后台后代仍存活。任一反例成功则原生命令模式不可发布。

本方案细化 [整体设计 §8](pishoo-wasm-db-redesign.md#8-ssh-与关闭) 的终端模型；真正不受限的本机管理员 shell 应走独立入口，不能与受限终端共用授权规则。

# App / Lib 审批接入约定

本约定自 2026-10-23 的审批协议调整生效。权限审批由宿主和 daccess 完成；批准权限不代表业务执行成功，也不代表接受好友。

## 响应与页面状态

| 场景 | HTTP / 响应 | 页面行为 |
| --- | --- | --- |
| 异步权限审批 | `202` + `status: pending_review` | 普通待办提示，保留输入，查询已有审批，不作为成功或通用错误 |
| 好友申请已受理 | `202` + 联系人、`delivery_status: queued` | 显示申请已提交／正在投递，由宿主后台继续 |
| 消息已入队 | `202` + 消息、`state: queued` | 显示本地消息，保留原消息编号，按消息状态刷新 |
| 好友申请已送达 | 联系人 `delivery_status: pending` | 等待对方接受；不表示已获其他接口权限 |
| 业务完成 | 原接口定义的 `200/201/204` | 才显示保存、发送或删除完成 |
| 审批拒绝／过期 | 状态查询 `denied/expired` | 停止本轮自动重试，保留输入，由用户决定是否重新申请 |

不能用 `response.ok` 判断业务已经完成，也不能把所有 `202` 都解释成权限审批。

## 异步模式（默认）

请求头为 `If-Reviewed: break`，省略时也使用此模式。命中 review 时，业务处理器尚未执行：

```http
HTTP/1.1 202 Accepted
Cache-Control: no-store
Location: /std/acl/status?id=12
Retry-After: 3
Content-Type: application/json

{"status":"pending_review","review_id":12,"status_url":"/std/acl/status?id=12"}
```

1. 先识别上述判别字段，再解析业务响应。普通业务 `202` 使用自己的响应模型。
2. 记录审批编号和原请求目标。每 3 秒左右查询状态即可，隐藏页面暂停前端轮询。原生 Contact / Message 后台使用既有 30 秒间隔。
3. `pending` 只查状态，不重复调用业务；`allowed` 才重试原操作。`consumed` 不是业务完成证明，必须重新鉴权并获取业务结果；额度可能已被其他匹配请求使用。
4. `denied/expired` 结束本轮；状态 404 视为本轮已失效。状态接口本身返回待审批时停止递归请求并提示暂不可查。
5. 后续仍可能再次进入 review；按新编号处理。不能因曾经批准就绕过正常鉴权。
6. 不直接请求响应中任意 URL。用正整数编号在原已认证目标构造 `/std/acl/status?id=ID`；经 DHTTP 转发的请求保留原目标前缀。
7. 旧宿主的 `400 + error: need_review` 可在过渡期按相同方式处理。普通 400 仍是失败。

页面文案建议：“正在等待对方授权。输入已保留，无需重复提交。”读取视图可自动查询并在批准后刷新；编辑操作应保留草稿，使用“查询审批状态”继续同一操作。不要在审批中清空输入、关闭编辑器、跳转成功页或重复创建消息。

## 实时等待模式

显式发送 `If-Reviewed: waiting`。宿主保留原请求，最多等待 300 秒；允许后直接继续原业务并返回其真实响应。单次允许仅放行选中的等待请求。

- 用户拒绝：`403 {"error":"review_denied"}`。
- 等待超时：`504 {"error":"review_timeout"}`；这不代表对方拒绝。
- 等待通道不可用：`503 {"error":"review_unavailable"}`。
- 客户端取消请求：释放实时待办，不写入持久审批或权限。

客户端等待期限需长于服务端审批期限，并提供取消入口。未收到服务器确认前，只能显示“请求处理中”，不能因响应缓慢就认定已经进入审批。希望立即明确显示待审批、允许离开页面的调用应选异步模式。

## 幂等与持久授权

审批编号标识授权轮次，不是业务幂等键。一次授权按已验证身份、SubjectId、method 和规范化路径匹配，不绑定 query 或正文。Message 重试保留 `client_message_id`；Journal 保留条目／留言编号和更新版本。不得在错误重试中生成新的业务编号。

`remember=false` 不写 ACL；异步单次额度在一次匹配调用进入业务时消费，业务失败也不会退还。`remember=true` 才保存持续生效的规则。接受好友与授予接口权限仍是独立操作。

## 当前实现覆盖

| 组件 | 审批处理 |
| --- | --- |
| 原生 Contact 投递 | 保存审批编号及对端主体；pending 只查状态，允许后继续，拒绝／过期终止本轮 |
| Message Lib | 同上，并保留消息编号、租约及 reviewing 状态；不消耗普通网络重试次数 |
| Profile / Calendar / Journal Lib | 无出站审批消费者；统一宿主授权在进入 guest 之前执行，未批准不执行写操作 |
| Workspace App | 区分审批 202 与消息／联系人入队 202；等待提示、草稿保留、查询状态后继续；联系人显示投递与好友确认阶段 |
| Introduction App | 各字段分别处理审批，其他可读字段继续展示；头像审批不会被误当成图片 |
| Calendar App | 读取等待状态可刷新，保存／删除等待时保持编辑器与输入，下一次操作先查询审批 |
| Journal App | 待审批使用普通状态提示，保留条目／留言草稿及幂等编号；查询状态后继续 |

浏览器的审批引用仅保存在当前页面会话，不保存凭据。关闭页面后，后台投递仍由 Contact / Message 持久队列负责；前端重新进入时按资源状态恢复显示。

Calendar 新建日程当前由服务端分配编号；一旦已获授权并开始业务执行，若响应在网络中断时丢失，不能自动重发创建请求。本轮前端仅自动刷新审批中的读取，Calendar 写入保持显式保存，不新增业务幂等协议。

# 静态文件 Range 与缓存策略规划

日期：2026-11-05。状态：宿主部分已实现并验证；头像接入仍为后续提案，未实施。

基线：拉取后的 `origin/main`，提交 `74222dc87932ef3e28740fe46a2367b7e0485f24`。
工作分支：`plan/static-range-cache`。原工作区的修改不带入此分支。

## 1. 范围与推荐方案

两个功能共用同一条静态响应流程：授权、选定并打开文件、读取元数据、判断条件、判断范围、构造文件流。

首版推荐：单段字节 Range；浏览器私有缓存且每次复用前核验；元数据弱 ETag 与 Last-Modified；保持现有文件流和原子替换方式。
这里的缓存是 HTTP 客户端缓存策略，不增加宿主文件内容缓存、代理缓存或数据库缓存。

2026-11-05 用户后续明确头像场景可以接受更新延迟，优先解决刷新后的显示等待。头像采用短期直接复用及后台核验，具体见 §3.1；不要求所有资源在显示前完成网络核验。

| 入口 | 首版处理 |
| --- | --- |
| 已安装 App `/app/<name>/…` | Range、条件请求及缓存策略的主要入口 |
| 原生 `/std/file/…` | 复用同一协议算法，保留现有目录和路由规则 |
| Jade 本地 App | Range 和条件请求可复用；响应保持 `no-store` |
| Profile 头像及 Workspace 头像展示 | 增补产品接入规划：允许短期缓存，先显示缓存、后台更新；分别由独立 Profile / Workspace 仓库实施 |
| WASM Lib、TCP 反代、DHTTP 转发 | 保留请求条件头与响应缓存头的现有传递，缓存语义由实际响应方决定 |

不增加清单字段、管理 API、SQL、配置开关、压缩协商或后台任务。首版也不按文件扩展名、`assets/` 路径或看似含哈希的文件名自动开启长期缓存。

## 2. 当前实现与约束

- `src/sandbox.rs::app_response` 为正式和本地 App 共用入口，负责路径校验、跳转、SPA 回退、文件打开和响应；目前为全部响应设置 `Cache-Control: no-store`。
- 正式入口在 `Sandbox` 读锁内选择目录并调用该函数。新增操作必须保持短暂持锁，不在此处扫描完整文件或等待响应传输。
- `src/routes.rs::static_file` 服务 `/std/file/…`，目前只有完整 GET/HEAD、类型和长度，未明确缓存策略。
- 两处使用 16 KiB 的 `ReaderStream`；HEAD 不读文件内容。App 读取通过 `package::app_file`，原生文件通过 `cap_std::fs::Dir`，各自的目录边界保持。
- `src/routes/access.rs::authorize` 在 App HEAD 中注入真实 `Pishoo-Viewer-Name` 并覆盖为 `no-store`。这项身份探测行为必须保留。
- 每次响应持有已打开文件；部署采用临时文件加原子 rename，不原地改写正在发送的文件。文件句柄并不能冻结同一 inode 被原地写入后的内容。

源工作区的 `AGENTS.md` 和 `design/` 是被忽略的本地约定，远端 main 不包含这些文件；本提案遵循已读取的约定，不把整套本地历史文档复制到新 worktree。

## 3. 缓存策略

| 响应 | 建议策略 | 原因 |
| --- | --- | --- |
| 正式 App / 原生文件的成功 GET，包括 206、SPA 回退 | `private, no-cache` | 浏览器可保存，复用前必须到宿主重新授权和核验；共享缓存不得存储 |
| 条件命中的 304 | 与对应 GET 相同 | 更新已有缓存条目的策略和验证器 |
| App HEAD，包括条件 HEAD | `no-store` | 响应带当前访问者身份，沿用授权层覆盖 |
| 原生文件 HEAD | `private, no-cache` | 元数据与对应 GET 一致，无正文 |
| Jade 本地 App | `no-store` | 保留开发时每次访问宿主的行为 |
| 静态入口的跳转、404、405、412、416 及其他错误 | `no-store` | 避免启发式缓存掩盖后续文件、安装或权限变化 |

授权拒绝和审批结果优先返回，不进入文件核验。对静态入口补齐错误响应策略时，范围限定在这些入口，不能把全站 Lib 或代理响应统一覆盖。

`no-cache` 允许存储，要求复用前核验；`no-store` 禁止存储，两者不互换。上述策略的依据为 [RFC 9111 §5.2.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2)。

公开 App 也先采用同一默认值：公开规则以后可以撤销，而长期新鲜缓存可以在有效期内跳过宿主。已交给客户端的历史内容无法通过撤销 ACL 收回。

### 3.1. 头像优先显示缓存

头像允许短暂陈旧，不以“每次先通过网络核验当前权限和版本”作为显示前提。缓存与条件请求的目标分别是减少显示等待和减少正文重传，只有 304 不能消除网络往返等待。

当前链路的具体问题：独立 Profile 的 `src/profile.rs::avatar` 已有 ETag / 304，但 `respond` 默认补 `no-store`；Workspace 的 `src/api/client.ts::readProfile` 请求头像时使用 `cache: 'no-cache'`，联系人头像 Blob 只由页面内 `ContactProfiles` 保存，刷新会丢失。因此只修改 Pishoo 的静态响应不会修复头像。

建议接入行为：

- Profile 成功头像 GET 和 304 使用 `private, max-age=300, stale-while-revalidate=86400` 作为初始建议值：5 分钟内可直接复用，之后允许在一天窗口内先使用旧副本、后台核验。具体时长是提案值，不是新增用户配置；错误、权限结果及写操作响应不套用该缓存策略。
- Workspace 取消头像请求固定 `cache: 'no-cache'`，普通资源请求允许浏览器按响应策略处理。浏览器或用户刷新仍可能要求核验，HTTP 缓存头本身不保证所有刷新都立即显示旧图。
- 为满足“刷新后先显示头像”的明确体验目标，Workspace 接入可跨刷新保存的头像副本（可采用 IndexedDB 保存 Blob、ETag 和核验时间），先读取本地副本展示，再发起非阻塞核验。现有 `ContactProfiles` 继续做页面内请求合并与 Blob URL 生命周期管理，不把临时 `blob:` URL 当作可持久化图片内容。
- 本地副本区分服务身份、当前真实访问者及头像所属身份；切换访问身份时隔离，退出时清理相应缓存。后台收到 304 保持图片，200 替换，403/404 删除副本并恢复默认头像；短暂网络失败可保留旧图至既定有效窗口。
- 上传或删除自己的头像后立即更新或移除当前用户的缓存；其他访问者在之后访问和核验时自然更新，不新增推送通知或宿主后台刷新任务。

这种策略接受缓存有效期间暂时显示历史头像，更新、删除或权限撤销可延迟反映；用户已认可头像更新无需即时同步。该选择限定在头像，不自动扩展到聊天内容、身份探测和其他业务数据。

后台核验与旧内容复用的 HTTP 依据为 [RFC 5861 §3](https://www.rfc-editor.org/rfc/rfc5861.html#section-3)。跨刷新本地展示属于 Workspace 产品行为，需要独立实现；不能只改响应头就宣称已经达到刷新即时展示。

## 4. 验证器与性能取舍

### 首版：弱 ETag，不扫描文件正文

从同一个打开句柄取得长度、设备号、inode、mtime 和 ctime（含可取得的纳秒部分），以这些值生成不暴露原始元数据的摘要，格式如 `W/"…"`。
这是元数据验证器，不是文件内容摘要，也不是发布包完整性证明。不能只使用包版本：现有约定允许目录内原子替换文件，新请求应立即看到替换结果。

`Last-Modified` 使用同一句柄的修改时间，按 HTTP 日期输出到秒，未来时间不超过本次响应 Date；日期不可可靠表达时省略该头及日期条件判断。ETag 保留高精度变化信息，客户端同时带条件时优先使用 ETag。

弱 ETag 支持通常的 `If-None-Match` 核验，但不能作为可靠分片拼接或 `If-Range` 的强验证器。首版不宣称提供可验证的断点续传：

- 普通单段 Range 可直接返回 206，满足媒体跳读和选段读取。
- 携带 `If-Range` 时，弱标签不能强匹配；宿主也没有证明日期具有强度的修订记录。因此首版保守回退完整 200，不能仅因日期相等就拼接旧数据。
- `If-Match: *` 对已找到文件成立；具体标签需要强比较，当前弱标签不能使其成立。
- 206 使用当前验证器及缓存策略；客户端不能把仅共享弱验证器的多个分片当成同一内容版本可靠合并。

这项边界依据 [RFC 9110 §8.8、§13.1.5、§15.3.7.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5)。

### 后续选项：强内容 ETag

如要求跨请求可靠续传，应增加文件内容的 SHA-256 强 ETag，再启用匹配 `If-Range` 的 206。
本轮不把“每次请求先完整读盘求摘要”作为默认实现：这会使小范围请求和条件 HEAD 也发生 O(文件大小) 的读取，削弱大文件 Range 的收益。

强验证器实施前需单独选定摘要来源：请求内流式计算的 I/O 成本，或有明确失效规则的文件摘要资源。后者需要列出具体状态、归属、替换规则和冻结接口差异；不能顺便加入全局摘要表，或把安装包摘要当作单文件摘要。

## 5. 条件请求

只在授权成功、方法允许、跳转和路径检查完成、真实文件已经打开之后处理。不存在的文件仍返回 404；SPA 回退使用实际 `index.html` 的验证器、长度和类型。

GET 和 HEAD 采用同一顺序：

1. 有 `If-Match` 时作强比较，不满足返回 412；否则才检查 `If-Unmodified-Since`。
2. 有 `If-None-Match` 时作弱比较，命中返回 304；否则才检查 `If-Modified-Since`。
3. 仍应返回 200 且方法为 GET，才处理 Range / If-Range。

标签列表、`*`、弱前缀和重复字段使用完整字段值语法解析，不使用简单字符串包含或无视引号的逗号拆分。非法标签条件返回 400 且 `no-store`；非法或重复的单值日期条件忽略，标签条件的优先级不变。以上非法输入处理是本提案的明确选择，实施时固定回归用例。

304 无正文，保留 ETag、Last-Modified（可用时）、Date、Cache-Control 和应保留的安全头。实施时发现 Axum 会为无长度的空 Body 自动补 `Content-Length: 0`，因此显式设置对应完整 200 表示的长度，避免非空资源的 304 被补为零；这是 RFC 9110 §8.6 允许的长度语义。HEAD 的 304 仍由授权层携带当前访问者身份并强制 `no-store`。

412 使用空正文和 `Content-Length: 0`。方法 405、缺失 404、跳转等正常检查结果不被条件请求改写成 304。

顺序以 [RFC 9110 §13.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2) 为准。

## 6. 单段 Range

仅 GET 解释 Range，成功文件响应声明 `Accept-Ranges: bytes`。HEAD 忽略 Range / If-Range，返回完整表示的元数据或条件响应，不读取正文。

假设文件长度为 10：

| 请求 | 结果 |
| --- | --- |
| 无 Range | 200，长度 10 |
| `bytes=0-3` | 206，`Content-Range: bytes 0-3/10`，正文 4 字节 |
| `bytes=4-` | 206，范围 4–9 |
| `bytes=-3` | 206，范围 7–9 |
| `bytes=0-99` / `bytes=-99` | 206，范围 0–9 |
| `bytes=10-` / `bytes=-0` | 416，`Content-Range: bytes */10`，空正文 |
| 未知单位、畸形范围、起点大于终点 | 忽略 Range，200 |
| 多段范围，包括重复 Range 字段 | 首版忽略整项范围请求，200，不只截取第一段 |
| 条件缓存命中且同时带 Range | 304，范围不再参与 |
| Range 同时携带首版无法强核验的 If-Range | 200，完整表示 |

空文件统一忽略 Range，返回 200、`Content-Length: 0`，避免构造 `0--1/0`；这是零长度表示可忽略 Range 的选择。416 使用 `no-store` 和空正文长度 0。

十进制数可能超过 `u64`：先校验数字语法，再按与实际文件长度的大小关系归一化；超大起点为不可满足、超大终点截到 EOF、超大后缀覆盖整个文件。不回绕、不 panic，不把溢出静默解析成零。

在打开句柄上 seek 到起点，以 `take(选段长度)` 限定读取，再接现有 16 KiB ReaderStream。完整 GET 也按选定长度限制读取，不把文件意外增长后的额外字节发送出去。文件意外缩短导致提前 EOF 应作为传输不完整处理，不能补零或把已发送的 206 追改为错误状态。

不新增自定义 Body、租约、并发名额或文件内容容器；丢弃 Body 沿现有所有权停止读取。原生静态入口的 Range 行为依据 [RFC 9110 §14](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)。

## 7. 代码落点与拟议契约差异

建议集中协议算法，保留各入口已有的文件选择和权限边界：

| 文件 | 拟议修改 |
| --- | --- |
| `src/static_files.rs`（新） | 接收已打开普通文件，生成验证器、条件和范围结果，构造有界流；解析 helper 均为模块内无状态函数 |
| `src/lib.rs` | 声明私有 `mod static_files` |
| `src/sandbox.rs` | `app_response` 保留签名、路径选择和文件打开，委托共用函数；错误和跳转策略在所属入口处理 |
| `src/routes.rs` | `static_file` 保留签名、cap_std 打开和目录 index 规则，打开后委托共用函数 |
| `src/development.rs` | 在 App 响应边界覆盖 `no-store`，包括错误和跳转，不新增开发状态 |
| `src/routes/access.rs` | 保留 App HEAD 身份和 `no-store` 行为；增加集成验收，只有必要时才调整函数体 |
| `Cargo.toml` / `Cargo.lock` | 如采用 `httpdate` 处理 HTTP 三种日期语法，将其声明为直接依赖；当前 lock 已含该包 |

用户要求先实施宿主部分后，本轮采用且仅新增以下跨模块无状态函数：

```rust
pub(crate) fn response(
    file: std::fs::File,
    media_path: &str,
    request: &http::Request<axum::body::Body>,
) -> crate::Result<axum::response::Response>;
```

该函数只处理文件响应，不重复鉴权或按路径重开文件。静态目录和 App 的区别由调用方选择文件，开发 `no-store` 与 App HEAD 身份覆盖保留在既有响应边界。
从阻塞上下文调用时只执行元数据、局部解析和 seek，不在 Sandbox 锁内读完整内容。`static_file` 的共用构造也放在其阻塞开文件阶段；返回后才消费异步流。

不增加自定义结构、字段、枚举、方法、持久化状态或其他跨模块接口；现有 `Sandbox.apps`、`app_response`、`static_file`、`package::app_file` 和 `development::router` 签名保持。
本轮宿主实现依据用户“开始实现，先支持宿主的”指令推进上述具体签名，并记录于本 worktree 的本地 `design/pishoo-interfaces.md`；Profile / Workspace 不在本轮实施范围内。

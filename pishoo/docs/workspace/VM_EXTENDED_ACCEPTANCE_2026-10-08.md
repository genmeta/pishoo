## 两个新问题及修复

### 双向并发发送出现 500

原消息 ID 为“秒级时间戳＋进程计数”。两台 VM 在同一秒使用同一计数时产生相同 ID，
而本地收发消息共用 `(contact_name, client_message_id)` 唯一键，导致入队失败。
Bob 日志确认为 SQLite `UNIQUE constraint failed`，不是 HTTP/3 重置。
见失败日志（`17-bob-concurrent-storage-error.json`）。

`pishoo/src/chat/service.rs` 现使用系统随机源生成 128 位随机 ID，编码为 32 字符十六进制，
不再依赖两端时钟、进程计数或重启次数。协议及库结构保持兼容。
复验时共入队 88 条短消息和 1 条 4000 字消息，每端该批次均为 89 条、无重复、全部完成投递。
见并发入队（`12-chat-concurrent-queued.json`）和
投递及分页核对（`13-chat-over-100-history.json`）。
后续实测至最终采样，未再记录 Chat 唯一键或存储错误。

### 聊天页只显示最早 100 条

实际历史达到 120 条时，后端正确返回第一页 100 条、第二页 20 条，页面只渲染 100 条，
最新一条不可见。证据见修复前采样（`13a-chat-pagination-bug-before.json`）。

`ChatPage.tsx` 现在沿 `next_cursor` 加载完整历史；刷新时保留已经送达的前缀，从第一条
尚未送达的消息开始读取后续页，同时更新重试状态及新消息。请求取消后不会覆盖缓存。
复验双方页面完整显示 122 条并自动显示互发的新消息；VM 重启后又完整显示最终的 128 条。
见 Alice 复验（`13b-alice-pagination-fixed.json`）、
Bob 复验（`13b-bob-pagination-fixed.json`）和
最终聊天视口（`23-alice-final-chat-ui.png`）。

## 需要按现有设计理解的行为

- 解除拉黑会恢复之前保存的访问规则快照；旧申请仍为 revoked，不会继续轮询。
  实测通过新申请确认当前授权后，原阻塞消息只投递一份。
- 正在投递的联系人申请有租约保护，删除返回 `409 / request is being delivered`。
  此时不能声称已取消；等待实际重试间隙后删除才返回 204，远端未收到该申请。
- 联系人页面换页会清空选择，选择范围为当前页；本次按现有设计分别删除末页 1 项和首页 20 项。
- 头像删除后旧 immutable URL 可能仍被浏览器缓存；公开资料的对端代理也有五分钟缓存。
  删除判定使用当前资料、删除后新原生头像请求及页面回退，不把旧缓存的 200 判作删除失败。
- 到期实测仅加速隔离 VM 的系统时钟；没有直接写 SQL 审批决定。时钟和 NTP 已恢复，
  因加速产生的过期记录时间戳会晚于宿主机最终采样时间，不代表真实等待了七天。
- 21 条分页记录直接准备在隔离库中，未配发证书或模拟 21 个认证用户。
  页面删除后联系人及规则均为零，残留的夹具保存记录也已通过 owner API 清理。
- SID 故障注入只改 Alice 的本地 Bob 身份记录，双方实际证书保持原样。
  恢复原 SID 后，原已批准身份的任务可重试并只送达一份；错误 SID 任务重试仍为 409。
